Review the security and performance impact of the proposed changes. Keep every worktree read-only. In each participating repository, inspect the diff from the supplied base commit and check `git status --short` for untracked files. Start with the changed behavior and follow its callers, dependencies, and data flows far enough to understand the impact. Focus on risks the change introduces or makes worse.

For work spanning repositories, trace a representative request, event, or background job from its entry point through the services that handle it. Check what each side actually sends, accepts, enforces, and assumes. Compare both implementations with the approved contract. When components deploy independently, check whether supported old/new version combinations preserve access controls, data handling, and resource limits.

For security, identify who controls the input, which component has authority, and where access to the resource is enforced. Check authorization and tenant isolation at the point of access, including paths that bypass the client UI. Follow sensitive data through responses, logs, telemetry, and errors. Inspect changed uses of untrusted input in commands, queries, file paths, and outbound requests. Review new dependencies or permissions when they expand what a component can access.

For performance, trace the cost of one user action or job across repositories. Look for costs that multiply at a boundary, such as a client request per row that triggers a database query per item, or retries at both the client and service layers. Check relevant limits on payload size, pagination, concurrency, queues, and timeouts. Inspect blocking work on UI or async execution paths and whether cancellation releases resources.

Support each finding with concrete evidence. For security, identify the input or caller, the missing or incorrect control, and the reachable consequence. For performance, give a measurement or a cost derived from the code, such as how request count grows with the number of items. Label estimates and state their assumptions. Use Hive’s check results, existing benchmarks, or available read-only observations when relevant. If impact depends on an unknown workload or deployment setting, identify what would verify it.

Report each defect once, against the lane that owns the correction. Include the relevant file and line, triggering conditions, impact, severity, and a focused correction. For a cross-repository issue, cite both sides and identify any coordinated change needed. On repeat review, verify the original failure path against the repair and respect findings the user has already accepted. Return an empty findings list when you find no concrete defects, and record material verification gaps in the summary.
